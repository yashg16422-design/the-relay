# 0008 — Stand-in calibrated from real calls, with refilling buckets

- Status: accepted            <!-- only Aloo changes this to accepted / rejected -->
- Date: 2026-11-13
- Phase / gate: D

## Problem
The brief says the stand-in must be calibrated from what was measured on the real service. The old stand-in had every delay and failure rate at 0, limits of 60 requests and 30,000 tokens per minute against real values of 30 and 8,000, replies of one short sentence, and sliding windows. Load results from it say nothing about the real service.

## Options
1. Keep the old stand-in and state its limits in the write-up.
2. Keep sliding windows but put in calibrated latency and limits (the CTO reviewer's cheaper suggestion).
3. **Refilling token buckets, per-step latency and billed tokens drawn from real calls** (implemented; `limit_model: token_bucket` in `standin/config.yaml`, which is generated by `analysis/calibrate_standin.py --write-config`). The old file is kept as `standin/config.legacy-2026-11-11.yaml`.

## Evidence
- Limits refill continuously: on 332 real responses the reset header equals used ÷ refill rate (median error 0.5 ms), and the real 429 of probe E3 says "Limit 8000, Used 5724, Requested 2945. Please try again in 5.0175s", which is exactly (5,724 + 2,945 − 8,000) ÷ 133.3. Files: `results/raw/limit_refill_analysis.json`, `results/raw/E3-20261112T190331Z-openai_gpt-oss-20b.json`.
- Latency per step is a lognormal fitted on 319 real model calls (`results/calibration_fit.json`). `results/calibration_report.md` compares 100 stand-in calls per step with the real spans: understand p50 +7.6% and p95 +6.0%, judge −6.6% and −5.1%.
- Requests per minute is 30: probe E2 had 30 calls accepted and the 31st refused. In flight: 20 simultaneous calls were all accepted (E4).

## Decision (builder's recommendation)
Option 3. A sliding window would let a refused request wait for a whole minute; the real service asks for seconds. That difference changes every ladder decision, so it is worth the extra code.

## What it costs
About 120 more lines in `standin/server.py`. Draft and repair latency rest on 19 and 10 real calls. Output-token counts were mostly measured under the old 100- and 120-token caps. Tokens per day (200,000) is from the docs only. The load slowdown (3.8 ms per extra request in flight) comes from one probe of tiny calls. The stand-in admits on input plus billed output; Groq admits on input plus the output cap.

## What would change our mind
A real burst that shows latency rising steeply with concurrency; a daily-limit 429 whose behaviour is not a refilling bucket; refitted draft latency (once 20 post-rework calls exist) more than 25% away from the current fit.
